# 接口数据与差分链路

先了解接口的数据方向，再选择 USB 或无线方案。这里的“输入 / 输出”均相对于 RTK 设备。

跨厂家搭配分别按产品章节操作：[其他厂家基站 → SwiftWing 移动端](../SwiftWing_R1_RTK_移动端/差分与Wi-Fi后台.md#third-party-base)、[SwiftWing 基站 → 其他厂家移动端](../SwiftWing%20R1-G%20RTK基站/USB与地面站输出差分.md#third-party-rover)。本页的设备参数、USB 身份与调试口定义仅适用于 SwiftWing 硬件；第三方接口和航向参数不套用本表。

## 外部接口各传什么

| 接口 | 输入到 RTK | RTK 输出 | 主要用途 |
| --- | --- | --- | --- |
| ANT1 | GNSS 射频信号 | 约 3.3 V 有源天线馈电 | 移动端定位主天线、基站参考天线 |
| ANT2 | GNSS 射频信号 | 约 3.3 V 有源天线馈电 | 移动端第二天线，用于双天线航向 |
| 原生 USB CDC0 | 配置、状态查询及配套管理请求 | 设备身份、参数、状态和回执 | SwiftWing QGC 管理，不是 MAVLink GPS 串口 |
| 原生 USB CDC1 | 不作为移动端差分输入 | 已启用出口的原始 RTCM3 字节流 | 主要供基站向 QGC 输出差分 |
| CAN | DroneCAN 差分、管理及支持的飞控状态消息 | 定位、精度、航向、节点状态；可选基站差分 | 移动端连接飞控的日常接口 |
| Wi-Fi HTTP | 浏览器 / QGC 管理请求 | 网页、状态、参数、日志文件 | 局域网 / 热点后台 |
| Wi-Fi UDP | 本版本不提供移动端 UDP 差分输入 | 基站主动发送原始 RTCM3，默认 13320 | QGC 监听接收 |
| Wi-Fi TCP | 客户端连接请求，不作移动端差分注入 | 基站原始 RTCM3 流，默认 2101 | 基站是服务器，QGC 是客户端 |
| UART0 调试口 | 3.3 V TTL 调试 / 救援通信 | ESP32 启动日志与配套管理响应 | 技术维护，不是接飞控 GPS2 的 GNSS 输出 |
| XT30 / USB 5 V / CAN 5 V | 对应电源 | 无定位数据 | 按硬件页区分电压 |
| FAN+ / FAN− | 无协议输入 | 受控风扇供电回路 | 基站散热，无转速反馈 |

TCP 2101 是原始流服务，**不是 NTRIP Caster**，无需挂载点或 NTRIP 账户。移动端 Wi-Fi 用于管理；把它和基站连到同一个热点，不会自动收到差分。

## 推荐的两条差分链路

```text
USB：基站 ANT1 → 基站 → 主板 USB CDC1 → SwiftWing QGC
                                                     ↓ MAVLink GPS_RTCM_DATA
无线：基站 ANT1 → 基站 → Wi-Fi UDP / TCP → SwiftWing QGC → 飞控
                                                           ↓ DroneCAN RTCMStream
                                                        移动端 → UM982 COM2

移动端位置 / 航向：ANT1 + ANT2 → UM982 → ESP32 → CAN → 飞控估计器
```

地面站与飞控之间使用飞控 USB 或遥测链路；移动端与飞控之间接 CAN。USB 方案中的“基站 USB”和“飞控 USB”是两个设备连接。基站无需再接到机载 CAN 总线。

QGC 必须启用差分注入。选项 **将 QGC 收到的差分注入已连接飞控** 会向已连接飞控注入；**绑定当前飞控反馈**只决定返回状态的观察对象，不限制注入对象。首次配置只连接本轮目标飞控，换机时重新核对反馈绑定。

## CAN 上的位置、航向和差分

移动端输出 DroneCAN v0 的 `Fix2` 定位信息和 `Auxiliary` 精度信息。航向按 `CAN_HDG_PROFILE` 选择兼容格式：1 为经典 PX4 路线，2 为 ArduPilot 的 `ardupilot.gnss.Heading`，3 为 AUTO。板端先按安装偏角生成机头方向，再发送给飞控。

经典 PX4 的 profile1 使用旧 Fix2 ECEF 航向扩展，并处理旧相对航向锁存；不能据此认为任意新版 PX4 main 都支持。双天线定向与外部基站改善位置是两套解算质量，位置固定不自动代表航向有效。

移动端从选定 CAN 源接收 `uavcan.equipment.gnss.RTCMStream`，校验并写到板内 UM982 COM2。`RTCM_SRC_ID=0` 自动选择有效来源；经飞控转发时源节点通常是飞控，而不是远处基站。不要把基站站号 `BASE_ID`、设备序列号和 CAN 节点号混用。

基站手动出口可启用 CAN 差分，适合专门设计的直连链路；它不替代常规地面站链路的配置。先用本教程 USB / UDP → QGC → 飞控 → CAN 方案完成首次接入。

## 板内串口与外部调试口的区别

- **UM982 COM1** 接 ESP32 GPIO8 / GPIO9，用于接收机配置、`BESTNAVA` 定位、`UNIHEADINGA` 航向和状态。
- **UM982 COM2** 接 ESP32 GPIO2 / GPIO3：基站从这里读取 RTCM；移动端向这里写入 CAN 收到的差分。当前固件管理此口，目标速率 115200、8N1。
- **外部 UART0** 接 ESP32 GPIO43 / GPIO44，用于主控调试。它与上述两个 UM982 端口不是同一路。

当前基站配置输出 `1006` 约每 5 秒、`1033` 约每 10 秒，以及 `1074 / 1084 / 1094 / 1124` 观测约每秒一次。USB / UDP / TCP 转发的是这些 RTCM 数据，不是飞控 MAVLink。`GPS1_RATE_MS` 改的是移动端定位 / 航向更新，不改变基站这些 RTCM 周期。

## 逐段确认是否成功

1. **基站接收机**：显示基站 RTCM 就绪，有新鲜参考与观测数据。
2. **QGC 接收**：有效帧持续增长，CRC 无持续错误，帧龄新鲜；“已连接串口”只是连接状态。
3. **飞控转发**：目标飞控在线，差分注入开启；PX4 开启 `UAVCAN_PUB_RTCM`，ArduPilot 确认差分包含目标 GPS 实例。
4. **移动端接收**：RTCM 接收计数增加、龄期更新、来源符合预期。
5. **接收机解算及飞控采用**：分别查看位置解、有效航向和估计器融合。前四步只证明传输，不能代替第五步。
